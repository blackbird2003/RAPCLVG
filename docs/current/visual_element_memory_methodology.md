# 基于视觉元素集合的长视频记忆检索方法体系

## 1. 背景与目标

当前 Seedance pipeline 的核心目标是：利用成熟的短视频生成 API，在 shot-by-shot 的生成过程中，通过记忆、检索、评估与精确提示，构建更长、更一致的视频。

早期流程主要将历史关键帧作为图像级记忆，通过文本相似度、图文相似度或经验规则进行检索。这种方式有两个明显问题：

1. **检索目标不够明确**：新 shot 可能只需要历史帧中的某个人物或物体，而不是整张图的场景、构图和所有可见元素。
2. **错误引用难以控制**：一张参考帧中同时包含“应参考元素”和“不应出现元素”时，视频模型可能把不该继承的内容也带入下一段。

因此，近期讨论形成了一套更显式的思路：把记忆检索从“图像与 prompt 的相似度问题”转化为“视觉元素集合的覆盖与排除问题”。

本文整理当前方法体系，包括：

- 视觉元素集合构建
- 元素结构定义
- 元素状态管理
- 基于视觉元素集合的 VLM 标注
- 历史关键帧评判
- 贪心覆盖选帧算法
- 含精确指代的 Seedance prompt 组织
- 当前已完成的初步验证与后续扩展方向

该方案仍是研究原型，但已经具备较清晰的工程落地路径。

## 2. 总体思想

对每一个新 shot，不再直接问：

```text
哪几张历史关键帧和当前 prompt 最相似？
```

而是拆成几个更可解释的问题：

```text
当前 shot 中哪些视觉元素需要从历史中继承？
哪些历史视觉元素明确不应该出现？
每张历史关键帧实际包含哪些已知视觉元素？
用尽量少的参考帧，能否覆盖当前所需元素，并尽量避免引入冲突元素？
```

最终，参考帧不仅作为图片输入 Seedance，还会附带文字说明：

```text
参考图 x 来自 shot y。
请参考其中的人物 A、物体 B。
不要引入其中的场景 C、人物 D。
```

这样可以把“为什么选这张图”“图中哪些部分应该被参考”“图中哪些部分是噪声”显式告诉视频模型，也方便后续失败分析。

## 3. 视觉元素定义

### 3.1 元素类别

第一版只保留三类视觉元素，避免过早构造复杂本体：

1. **角色 character**
   - 有运动、姿态、神态、语言或行为变化的实体。
   - 例如：穿绿色衣服的金发小男孩、戴王冠的孤独国王、好奇警惕的狐狸。

2. **场景 scene**
   - 宏观背景或空间环境，由图像整体判断。
   - 例如：布满沙尘的微小圆形星球、地球的广阔金色沙漠、咖啡店内部。

3. **物体 object**
   - 图中可检测、可分割、可被局部引用的视觉对象。
   - 例如：小星球上的红玫瑰、金色的小飞船、由发光立方体组成的桌子。

### 3.2 命名原则

元素名称应尽量具体，描述“特定指代对象”，而不是泛泛的类别名。

推荐：

```text
生长在小王子星球上的红玫瑰
穿绿色衣服的金发小男孩
由发光立方体组成的桌子
```

不推荐：

```text
花
男孩
桌子
```

这样做的原因是：后续检索和排除都依赖元素 ID。如果名称过泛，不同 shot 中同类但不同指代的对象会发生冲突。

### 3.3 元素应存储的信息

当前原型中，一个元素至少包含：

```text
id: 稳定标识符，例如 element-0001
name: 具体名称
type: character / scene / object
introduced_at: 首次引入的 shot
notes: 简短备注
```

示例：

```json
{
  "id": "element-0004",
  "name": "小星球上的红玫瑰",
  "type": "object",
  "introduced_at": "shot-0001",
  "notes": "位于星球上的一朵红玫瑰，是场景内的标志性物体"
}
```

后续可扩展字段包括：

- aliases：别名或同义表达
- visual_description：更详细的视觉描述
- importance：全局重要性
- first_seen_frame：首次被 VLM 确认出现的关键帧
- last_seen_frame：最近一次出现的关键帧
- canonical_frames：该元素的代表参考帧

## 4. 视觉元素集合构建

### 4.1 Prompt 驱动的集合维护

当前第一版只考虑从剧本 prompt 中构建元素集合，不从图像中新发现元素。

对每个 shot，输入：

```text
已有元素集合
此前 shot 的原始 video prompt
当前 shot 的 video prompt
```

要求 LLM 判断：

1. 当前 prompt 是否提到已有元素。
2. 当前 prompt 是否引入新的视觉元素。
3. 新元素属于角色、场景还是物体。
4. 新元素名称是否足够具体。

模型需要保守插入：只有当 prompt 中确实出现新的连续性相关实体时才加入集合。

### 4.2 为什么暂不从图像中新发现元素

生成画面中可能出现 prompt 没写出的补全细节，例如咖啡机、窗户、背景行人。这些元素有时也会影响后续一致性。

但是，开放式图像发现会带来额外问题：

- VLM 可能产生大量无关物体。
- 元素集合会快速膨胀。
- 同一元素跨帧对齐更困难。
- 新发现元素是否值得长期记忆需要额外判断。

因此，当前阶段先把集合构建限制在 prompt 驱动范围内，使验证目标更清晰。未来可以加入“VLM 提议新元素，LLM 决定是否入库”的机制。

## 5. 元素状态管理

对每个新 shot，已有元素不只是“相关或不相关”，而应被分配为几种状态。

### 5.1 状态定义

1. **应参考 should_reference**
   - 当前 shot 需要继承该元素的视觉一致性。
   - 例如同一角色再次出现、同一标志性道具继续出现、同一场景延续。

2. **应排除 should_exclude**
   - 根据当前 prompt 可以明确判断该元素不应该出现在画面中。
   - 例如已经换到另一个星球，旧星球上的国王和王座不应出现。
   - 该状态应谨慎使用：仅仅“prompt 没提到”不等于“应排除”。

3. **可选/不确定 optional_or_uncertain**
   - 可能有用，但 prompt 没有给出足够证据要求它出现或禁止它出现。
   - 这类元素可作为弱信号，但不应主导检索。

4. **新元素 new**
   - 当前 prompt 新引入的元素。
   - 新元素会加入集合，但通常无法从历史帧中检索到对应参考。

### 5.2 状态判定原则

状态判定应遵循以下原则：

- 角色跨 shot 反复出现时，通常应参考。
- 当前场景明确延续时，场景应参考。
- 当前场景明确切换时，旧场景可能应排除。
- 某个历史物体如果容易被误带入新画面，并且新 prompt 与其不兼容，应排除。
- 动作、姿态、表情、镜头运动通常不是全局元素，除非它们本身是连续性目标。
- 不确定时优先标为 optional_or_uncertain，而不是 should_exclude。

## 6. 基于视觉元素集合的 VLM 标注

### 6.1 标注目标

VLM 标注不是开放式目标检测，而是闭集识别：

```text
给定当前已知视觉元素集合，判断这张历史关键帧中出现了哪些元素，并给出边界框。
```

这样可以让不同关键帧的标注共享同一套元素 ID，便于检索、评分和可视化。

### 6.2 标注输入

对一张关键帧，输入：

```text
图像
当前元素集合
每个元素的 id、name、type、notes
```

要求 VLM 输出：

```text
visible_elements:
  - id
  - bbox
  - 可选说明
```

### 6.3 场景元素的边界框

场景是图像整体属性，不适合让 VLM 画局部框。当前约定：

```text
scene 类型元素如果被判定可见，其 bbox 统一为完整图片边框。
```

角色和物体则使用 VLM 返回的局部 bbox。

### 6.4 标注记录

一张历史关键帧的标注记录可理解为：

```json
{
  "frame_id": "shot-0004/keyframe0",
  "shot_id": "shot-0004",
  "image_path": "...",
  "visible_elements": [
    {
      "id": "element-0001",
      "bbox": [123, 80, 430, 710]
    },
    {
      "id": "element-0008",
      "bbox": [0, 0, 1280, 720]
    }
  ]
}
```

该记录本身不依赖未来 shot 的需求。它只是描述“这张图里有什么已知元素”。

## 7. 历史关键帧评判

当处理新 shot 时，不需要重新调用 VLM 标注所有历史图。只需将当前 shot 的元素状态映射到已有标注记录上。

例如当前状态为：

```text
element-0001 小王子: should_reference
element-0004 红玫瑰: should_exclude
element-0005 外太空: optional_or_uncertain
```

某历史关键帧中可见：

```text
element-0001
element-0004
```

则该帧的评判结果为：

```text
应参考命中: 小王子
应排除命中: 红玫瑰
可选命中: 无
```

这一步成本很低，且具有很强的可解释性。

## 8. 候选帧统一打分

### 8.1 基本思想

第一版选帧算法应尽量简单、可解释。无论是普通 top-k 选择，还是开启集合覆盖的贪心选择，都可以复用同一个打分函数：

```text
Score(f | covered)
  = 应参考元素奖励
  + 可选元素弱奖励
  - 应排除元素惩罚
```

其中 `covered` 表示此前已选参考帧覆盖过的应参考元素集合。

当不开启集合覆盖时，可以令所有应参考元素始终使用同一权重，直接按 `Score(f)` 取 top-k。这是一个重要的基础消融方案，在剧本较简单、元素冲突较少时可能已经有效。

当开启集合覆盖时，每选中一张参考帧，就更新 `covered`。下一轮打分时：

```text
未覆盖的应参考元素：高权重
已覆盖的应参考元素：低权重
```

这样不需要额外引入复杂的边际收益公式或冗余惩罚。算法会自然倾向于补足尚未覆盖的视觉元素，同时仍允许重复参考同一元素获得少量稳定性收益。

### 8.2 元素权重

第一版可使用简单固定权重：

```text
character: 3.0
scene:     2.0
object:    1.5
```

角色通常最重要，因为人物身份、服装和形象一致性对长视频观感影响最大。场景次之。物体权重略低，但标志性道具可在后续通过 LLM 或人工配置提高权重。

### 8.3 状态权重

推荐第一版状态权重：

```text
uncovered_reference_weight: 1.0
covered_reference_weight:   0.2
optional_weight:            0.1
exclude_weight:             0.5
```

这里 `exclude_weight` 默认不宜过大。原因是“应排除元素”可以同时通过精确指代 prompt 要求 Seedance 不要参考；如果惩罚过强，可能会错过包含关键应参考元素的历史帧。第一版可先使用 0.5，后续再根据错误引用情况调节。

### 8.4 可见质量

角色和物体可根据 bbox 面积估计可见质量：

```text
bbox 面积 < 画面 1%:      0.3
bbox 面积 1% - 10%:       0.6
bbox 面积 > 画面 10%:     1.0
```

场景元素可见质量暂定为 1.0。

未来可加入：

- 中心度
- 遮挡程度
- 清晰度
- 人物是否完整
- VLM 置信度

### 8.5 推荐公式

```text
Score(f | covered)
  = Σ reference_weight(e | covered) * type_weight(e) * quality(f, e),
      e ∈ visible(f) ∩ should_reference

  + optional_weight * Σ type_weight(e) * quality(f, e),
      e ∈ visible(f) ∩ optional_or_uncertain

  - exclude_weight * Σ type_weight(e) * quality(f, e),
      e ∈ visible(f) ∩ should_exclude
```

其中：

```text
reference_weight(e | covered)
  = uncovered_reference_weight, if e not in covered
  = covered_reference_weight,   if e in covered
```

第一版暂不加入杂讯惩罚和时间近邻奖励。原因是：

- 如果某个历史元素明确不该出现，应由状态管理标为 `should_exclude`。
- 未被 prompt 提到的元素不一定是噪声，过早惩罚可能误伤可用参考帧。
- 长期记忆检索本来就可能需要很久之前的场景或角色，时间近邻奖励容易削弱这一目标。

后续如果观察到明显的错误引用，可再加入较小的中性元素惩罚或其他质量项作为消融。

## 9. 贪心覆盖选帧算法

### 9.1 为什么不能只取 top-k

如果直接选择单帧分数最高的 top-k，常见问题是：

- 多张参考帧覆盖同一个主要角色，彼此冗余。
- 一个重要道具或场景没有被任何帧覆盖。
- 高分帧中夹带的冲突元素被忽略。

因此，最终选择应考虑“帧集合”的覆盖效果，而不是单帧独立排序。

不过第一版不需要设计独立的复杂 `MarginalGain`。集合覆盖只通过第 8 节中的动态 `reference_weight(e | covered)` 实现：未覆盖元素高权重，已覆盖元素低权重。

### 9.2 问题定义

对当前 shot：

```text
R = 应参考元素集合
X = 应排除元素集合
O = 可选/不确定元素集合
C = 候选历史关键帧集合
K = 参考帧数量上限
```

目标是选择一个帧集合 `S`：

```text
S ⊆ C, |S| <= K
```

使得：

```text
尽可能覆盖 R
尽可能少包含 X
必要时保留少量 O 作为弱辅助
```

### 9.3 两种选择模式

同一个 `Score(f | covered)` 可以支持两种模式：

1. **Static Top-K baseline**
   - `covered` 始终为空，或所有应参考元素始终使用同一权重。
   - 对所有候选帧独立打分，直接选前 `K` 张。
   - 这是最简单的消融基线。

2. **Greedy Coverage**
   - 初始 `covered = {}`。
   - 每选中一张帧后，把该帧中可见的应参考元素加入 `covered`。
   - 下一轮中，已覆盖元素降权，未覆盖元素保持高权重。
   - 这样算法会倾向于选择互补参考帧，而不是重复选择只包含同一元素的高分帧。

### 9.4 贪心流程

维护：

```text
selected = 已选参考帧
covered = 已被覆盖的应参考元素
```

### 9.5 停止条件

建议使用三个停止条件：

1. 已选帧数达到上限 `K`。
2. 所有应参考元素已被覆盖。
3. 当前最佳候选帧的 `Score(f | covered) <= 0`。

第三个条件很重要：当剩余帧只会引入冲突，或几乎没有可用参考价值时，不应为了填满槽位而提交更多参考图。

### 9.6 伪代码

```python
def select_reference_frames(candidates, states, max_frames):
    required = {e for e, s in states.items() if s == "should_reference"}
    excluded = {e for e, s in states.items() if s == "should_exclude"}
    optional = {e for e, s in states.items() if s == "optional_or_uncertain"}

    selected = []
    covered = set()

    while len(selected) < max_frames:
        best_frame = None
        best_score = 0.0

        for frame in candidates:
            if frame in selected:
                continue

            score = compute_score(
                frame=frame,
                covered=covered,
                required=required,
                excluded=excluded,
                optional=optional,
            )

            if score > best_score:
                best_score = score
                best_frame = frame

        if best_frame is None:
            break

        selected.append(best_frame)
        covered.update(best_frame.visible_elements & required)

        if covered >= required:
            break

    return selected
```

### 9.7 选择结果应保留解释

每张被选中的参考帧都应记录：

```text
frame_id
source_shot
score_at_selection
newly_covered_elements
already_covered_elements
excluded_elements_in_frame
optional_elements_in_frame
selection_reason
```

这对调参和论文分析都很重要。

## 10. 含精确指代的 Prompt 组织

### 10.1 基本原则

Seedance 的图片输入不是自解释的。若只提交参考图，模型可能不知道：

- 应参考图片中的谁。
- 应参考图片中的哪个道具。
- 是否应继承图片中的场景。
- 哪些可见内容只是历史噪声。

因此，每张参考图都应附带精确指代说明。

### 10.2 总体结构

第一版 Seedance 任务 prompt 可以采用五段式结构：

```text
[前序完整剧本]
以下是当前 shot 及其之前的 shot 级描述，仅用于理解已发生剧情、人物关系、场景切换，以及理解哪些历史元素不应出现在当前镜头中。
当前任务只生成 shot-i。不要生成其他 shot 的内容，也不要引入尚未在前序剧本或当前 shot 中出现的人物、场景或物体。

shot-0001: ...
shot-0002: ...
shot-i: ...

[1. 当前 shot 的生成任务]
现在请只生成 shot-i：

{current_video_prompt}

[1a. 非 cut / Smooth 连续性说明（仅在 Smooth 模式下加入）]
如果本 shot 是非 cut 且启用 Smooth 模式，则输入媒体中的 Video 1 是上一段原始视频的尾部片段。
当前 shot 不是从零开始生成，而是要向后延长 Video 1：新生成内容应从 Video 1 最后一帧之后的下一时刻开始，延续其中的人物动作、物体运动、镜头运动方向和速度，以保证运动连续。
不要把 Video 1 当作普通风格参考图，不要重新生成一个相似开头，不要突然跳到另一个姿态或景别。
不要倒回、重复、暂停、复刻、重播或把 Video 1 的任何部分再次包含在新生成视频中。

输入媒体编号规则：
- Video 1：上一段原始视频的尾部片段，仅用于时间延长与运动连续性。
- Image 1、Image 2、...：Video 1 之后的静态历史参考图片，用于视觉元素一致性。
- 下文中的“参考图片 Image 1”指第一张静态参考图片，不是 Video 1。

[2. 本 shot 的视觉元素计划]
本镜头应参考历史帧并保持一致的历史元素：
- ...

本镜头不应引入的历史元素：
- ...

本镜头可选参考但不要求出现的历史元素：
- ...

本镜头prompt中新出现的元素：
- ...

[3. 参考图使用说明]
以下参考图片仅用于保持指定视觉元素的一致性，不代表整张图都应被复刻。

参考图片 Image 1 来自 shot-xxxx：
应参考其中的：
- ...
不应引入其中的：
- ...

参考图片 Image 2 来自 shot-yyyy：
应参考其中的：
- ...
不应引入其中的：
- ...

[4. 总体约束]
当前 shot 的生成任务优先级最高。
前序完整剧本仅用于上下文理解，不是要求本镜头包含所有已发生内容。
只参考上述明确指定的视觉元素。
不要因为参考图中出现其他历史内容，就将其加入当前画面。
如果参考图说明与当前 shot 描述冲突，以当前 shot 描述和本 shot 的视觉元素计划为准。
```

这五段的职责分别是：

- 前序完整剧本：帮助模型理解已发生剧情、人物关系和排除理由，同时避免未来 shot 内容泄漏到当前生成。
- 当前 shot 的生成任务：明确本次真正要生成的内容；Smooth 模式下必须在这里说明“向后延长 Video 1”，避免模型把输入视频误当作普通参考素材。
- 本 shot 的视觉元素计划：在 shot 级别说明哪些历史元素应参考、不应引入、可选。
- 参考图使用说明：在图像级别说明每张静态参考图片中哪些内容可用、哪些内容不可用；Smooth 模式下需明确区分 Video 1 和 Image 编号。
- 总体约束：再次强调当前 shot 优先，前序完整剧本和参考图都只是辅助。

### 10.3 Shot 级元素计划与逐图指代

Shot 级元素计划和逐图参考说明都需要写，但二者含义不同。

Shot 级元素计划回答：

```text
当前镜头整体需要哪些历史元素？
当前镜头整体不应该出现哪些历史元素？
哪些历史元素只是可选参考？
```

逐图指代回答：

```text
某张被选中的静态参考图片中，哪些可见元素是本次提交它的原因？
某张静态参考图片中虽然可见、但不应该被模型带入当前画面的元素是什么？
```

例如：

```text
本镜头应参考并保持一致的历史元素：
- 穿绿色衣服的金发小男孩
- 好奇警惕的狐狸

本镜头不应引入的历史元素：
- 戴王冠的孤独国王
- 国王的小小王座

参考图片 Image 1 来自 shot-0008：
应参考其中的：
- 好奇警惕的狐狸
- 地球的广阔金色沙漠
不应引入其中的：
- 无

参考图片 Image 2 来自 shot-0004：
应参考其中的：
- 穿绿色衣服的金发小男孩
不应引入其中的：
- 戴王冠的孤独国王
- 国王的小小王座
```

这样即使某个应排除元素没有出现在选中的参考图片中，模型也仍然知道它不该出现在当前 shot；反过来，如果某张参考图片夹带了不应参考的元素，也能被单独约束。

### 10.4 与元素状态的关系

对一张被选参考帧：

```text
应参考 = visible(frame) ∩ should_reference
不应引入 = visible(frame) ∩ should_exclude
可选 = visible(frame) ∩ optional_or_uncertain
```

Prompt 中应优先写“应参考”和“不应引入”。可选元素可以不写，或写成弱约束：

```text
可作为氛围参考，但不是必须出现：...
```

第一版建议少写可选元素，避免提示过长。

### 10.5 高风险参考帧

如果一张图同时包含强应参考元素和强应排除元素，应谨慎选择。

若不得不选择，应明确写：

```text
该图中的 X 仅是历史画面中的旧元素，本镜头不应出现。
```

但如果该图的应排除元素是大面积场景或主要人物，通常应优先放弃这张图，除非没有其他可用参考。

## 11. 与现有 Seedance Pipeline 的关系

### 11.1 与 cut / non-cut 的关系

视觉元素检索不应只在 cut 段运行。

即使是非 cut 段，当前 prompt 中也可能出现上一段尾部没有、但历史记忆中存在的元素。例如角色拿回旧道具，或镜头回到某个标志性空间。因此，候选关键帧查询应作为主体机制，在 cut 和 non-cut 段都可运行。

非 cut 段的短期连续性可由 Smooth / Last frame only / 近端历史视频输入机制处理；视觉元素记忆则负责中长期一致性。

### 11.2 与 Smooth 模式的关系

Smooth 模式关注相邻两段视频的运动连续性：

```text
上一段尾部短视频输入 Seedance
生成后通过 RIFE 等方法处理拼接处
```

视觉元素集合关注跨 shot 的语义与视觉身份一致性：

```text
哪些角色、场景、物体应该被继承
哪些历史内容不应误入当前画面
```

二者是互补关系，不应混为一个模块。

### 11.3 与原有窗口记忆的关系

长期方向上，可以考虑弱化原 StoryMem 的窗口记忆，让非 cut 段主要依赖近端尾段视频维持短期连续性；同时把候选关键帧查询作为主体记忆机制，在所有 shot 中运行。

原有窗口/近期记忆仍可作为消融项保留，用于比较：

- 无视觉元素检索
- 图文相似度检索
- 视觉元素贪心覆盖检索
- 视觉元素检索 + Smooth 连续性

## 12. 当前初步验证

已有原型脚本完成了以下验证：

1. 对小王子剧本逐 shot 构建 prompt-derived 视觉元素集合。
2. 对每个 shot 输出已有元素状态和新元素。
3. 使用 Seed2.1 Turbo 对历史关键帧进行闭集 VLM 标注。
4. 对每个新 shot 的历史关键帧进行状态映射评判。
5. 输出标注和评判可视化：
   - 当前帧标注：显示元素 bbox。
   - 历史评判：绿色表示应参考，蓝色表示应排除，黄色表示不确定。

这验证了两个关键前提：

```text
LLM 能较稳定地维护短剧本中的视觉元素集合。
VLM 能在已知元素集合约束下，对关键帧进行可用的闭集标注。
```

下一步自然是把这些标注记录用于参考帧选择和精确指代 prompt 生成。

## 13. 建议的第一版实现边界

第一版工程实现可以保持非常轻量：

1. 不训练模型。
2. 不做开放式新元素发现。
3. 不做复杂图像 embedding 检索。
4. 只使用：
   - LLM 元素集合维护
   - VLM 闭集标注
   - 规则化打分
   - 贪心覆盖选帧
   - 模板化精确指代 prompt

推荐输出调试信息：

```text
当前 shot 的元素状态表
每张候选帧的可见元素
每张候选帧的 base_score
每轮贪心选择的 marginal_gain
最终选中帧
最终参考图 prompt 片段
```

这样即使生成效果不好，也可以定位问题来自：

1. 元素集合维护错误。
2. 元素状态判断错误。
3. VLM 标注错误。
4. 打分权重不合理。
5. 贪心选择策略不合理。
6. Seedance 没有遵循指代 prompt。

## 14. 后续扩展方向

### 14.1 元素重要性估计

目前元素权重只依赖类型。未来可让 LLM 判断当前 shot 中每个元素的重要性：

```text
核心主体
重要背景
辅助道具
弱氛围元素
```

并动态调整权重。

### 14.2 Canonical Frame

对每个元素维护若干代表帧：

```text
最清晰的人物正面帧
最完整的场景帧
最适合作为道具参考的局部帧
```

这样可以减少每次从所有历史帧中搜索的成本。

### 14.3 图像质量与遮挡判断

VLM 标注可扩展为：

```text
是否清晰
是否被遮挡
是否完整
是否适合作为参考
```

这些可直接进入可见质量评分。

### 14.4 负面参考学习

如果某些元素经常被错误带入，可以积累 failure log：

```text
某参考帧导致某应排除元素被生成
```

后续在选帧中提高该类冲突惩罚。

### 14.5 与向量检索结合

视觉元素检索不一定完全替代向量检索。可以采用两阶段：

1. 用视觉元素状态做硬过滤和覆盖目标。
2. 在候选帧内用 CLIP / VLM embedding / 图像质量做辅助排序。

### 14.6 图像中新元素发现

未来可引入：

```text
VLM 从生成结果中发现 prompt 未写明但稳定出现的视觉元素。
LLM 判断该元素是否值得加入全局集合。
```

这适合处理生成模型自动补全出的稳定背景物体、服装细节和标志性视觉设计。

## 15. 小结

这套方法的核心价值是把长视频记忆从“模糊相似度检索”变成“显式视觉元素调度”。

它要求系统在每个 shot 前明确回答：

```text
我需要继承什么？
我必须避免什么？
每张历史图能提供什么证据？
最少需要哪些图才能覆盖这些证据？
如何告诉视频模型正确使用这些图？
```

当前方案足够轻量，能够接入现有 Seedance pipeline；同时又有较好的可解释性和扩展空间，适合作为后续 Memory Selector 改进的主线之一。
